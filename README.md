# FortiGate-Format Log Triage (Python)

A small SOC-style tool that reads firewall logs in the FortiGate key=value format, groups noisy events into a
handful of prioritised incident tickets, and writes a report an L1 analyst could work from: severity, evidence
log lines, indicative MITRE ATT&CK technique, and a recommended first action.

> **Read this first.** The logs in this repo are **synthetic**. They follow the FortiOS key=value layout as I
> understand it from Fortinet's public documentation, but they were generated by `tools/gen_logs.py`, not exported
> from a real FortiGate, and exact `logid` values and field sets vary by FortiOS version. This project shows how I
> approach log analysis and alert triage; it is **not** evidence of administering a production FortiGate.
> All external addresses are from the RFC 5737 documentation ranges, so nothing points at a real third party.

## What it does

```
 firewall logs --> parser --> detectors (6) --> group into bursts --> rank by severity --> report.md + incidents.json
 (key=value)      skips bad    scan, brute force,   one campaign =       critical > high     ticket per incident:
                  lines        exposure, exfil,     ONE ticket, not      > medium > low      evidence, MITRE id,
                               IPS, malware / C2    hundreds of alerts                       recommended L1 action
```

| Detector | Looks for | Severity logic |
|---|---|---|
| `scan` | many denied targets from one source in a burst (port scan vs host sweep) | external = medium (internet background noise); **internal source = high** (possible compromised host) |
| `bruteforce` | repeated failed firewall-admin logins; spraying vs brute force | 5+ failures = medium, 20+ = high, **login success after failures = critical** |
| `exposure` | internet-sourced session **accepted** to RDP/SMB/Telnet/FTP/VNC/MS-SQL | high (a policy allowed it) |
| `exfiltration` | large, upload-heavy volume to an external IP | over threshold = medium, 5x threshold = high; approved backup destinations allowlisted |
| `ips` | IPS alerts with high/critical vendor severity | **same attack ranks lower if blocked** than if it got through |
| `malware` / `c2` | antivirus detections; traffic to a threat-intel blocklist | allowed contact with a bad IP = critical, denied attempt = medium |

Triage ideas built in: **bursts** (a quiet gap starts a new incident, so one attacker is one ticket), **allowlists**
for the authorised vulnerability scanner and the backup job (tuning, as in a real SOC), and **severity that reflects
the outcome**, not just the vendor label.

## Run it

```bash
python3 tools/gen_logs.py --out demo --seed 7     # 20,175 synthetic events, 11 injected incidents + benign noise
python3 -m triage demo/sample.log --out-dir demo/out
python3 -m unittest discover -s tests             # 36 tests
scripts/run_demo.sh                               # all of the above
```

Standard library only; developed and tested on Python 3.13. An example of the output is in [`examples/sample_report.md`](examples/sample_report.md).

## Results on the synthetic day

20,175 events (about 18,000 normal sessions, 1,500 inbound web requests, admin logins, plus the injected activity)
produced **11 incidents: exactly the 11 that were injected, with the expected severity, and none from the benign noise**
(an admin mistyping a password twice, the approved scanner, the nightly backup).

One injected attack is **deliberately missed**: a low-and-slow scan sending one probe every 10 minutes for 12 hours. Burst-based
rules cannot see it. It is listed as a known limitation and asserted in the tests, not hidden.

## How it was tested

* **Unit tests at every threshold boundary** (14 vs 15 scan targets, 4 vs 5 failed logins, bytes just under/over the
  upload limit), plus allowlists, quiet-gap splitting and the severity table.
* **End-to-end test** that generates the day, runs the real CLI, and compares the incidents with the ground truth.
  It also checks deterministic output, sorting, one malformed line being skipped, and a non-zero exit for a missing file.
* **Mutation check.** I deliberately broke the code four ways (reverted the spray/brute-force rule, shifted a threshold by
  one, ignored the scanner allowlist, stopped down-ranking blocked attacks) and confirmed the suite fails each time.
* While building it, reading the output (not just counting incidents) caught two real bugs: brute force on three accounts
  was mislabelled as spraying, and a byte count was shown as "MB" while computed as MiB. Both are fixed and covered by tests.

## Limitations (honest list)

* **Synthetic data, written alongside the detectors by one author.** 100% on this data shows the pipeline works; it says
  nothing about accuracy on real traffic. Thresholds would need tuning against a real network's baseline.
* Not exported from a real FortiGate; real logs have many more fields and vary by FortiOS version.
* No state across runs, no correlation between detectors (for example, a scan followed by an accepted session from the same IP),
  no beaconing detection, IPv6 untested, timestamps treated as naive local time.
* ATT&CK technique ids are indicative starting points for an analyst, not a verdict.
